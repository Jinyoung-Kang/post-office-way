## 4. 구조 개선 (리팩터링 — 동작은 그대로)

현재: 라우터 10개가 SQL 을 직접 실행하고, `api/services/*` 는 SQL·규칙·HTTP 오류(상태 코드)·캐시·응답 모양이 한 파일에 섞여 있습니다.
의존 방향도 거꾸로인 곳이 있습니다 — 워커 쪽 계산(`calc/runner.py`, `walk/compute.py`)이 API 계층의 `api.cache` 를,
`calc/runner.py`·`routers/dq.py` 가 수집기 안의 `collector.dq.rules` 를 import 합니다.
'최신 완료 계산 실행' 조회가 7곳, 레벨 검증 4곳, farKm 변환 6곳에 따로 있습니다.

목표 (새 인프라·인터페이스 계층 없이, 이 규모에 맞게):

```
api/routers/*.py      HTTP 만 — 입력 검증·응답 코드·캐시 헤더. 도메인 오류를 HTTP 상태로 바꾸는 곳은 api/errors.py 하나
      ↓
atlas/<기능>/service.py   규칙·흐름 (HTTP 를 모름 — NotFound/Conflict/Invalid 같은 도메인 오류만)
atlas/<기능>/queries.py   SQL — Connection 을 받아 dict 를 돌려주는 평범한 함수 (리포지토리 클래스·ABC 없음)
      ↓
atlas/domain/*         React·DB 없는 순수 규칙 (탐욕 배치, What-if 요약, 영업 상태, 파라미터 해석)
atlas/core/*           설정·DB·로그·캐시(버전 키)
```

| 단계 | 내용 | 회귀를 잡는 테스트 |
|---|---|---|
| A0 | 공용 조회·오류·캐시 정리 — `atlas/runs.py`(최신 완료 계산 실행), `domain/errors.py`, `domain/params.py`(farKm·레벨), 품질 규칙을 `atlas/dq.py` 로(수집기 밖), `run_sql_file` 을 `core.db` 로, 캐시를 `core` 로 옮기고 버전 키(R4 와 함께) | 기존 189개 + 먼저 추가할 응답 고정 테스트 |
| A1 | 순수 함수를 domain 으로 — 배치 제안 탐욕 알고리즘(`plan.py:30-124`), What-if 요약, 영업 상태 판정 | 기존 단위 테스트 + What-if 부분 재계산 = 전체 재계산 동등성 테스트 |
| A2 | 섞인 정도가 큰 기능부터 service/queries 로 — whatif, plan, overview(라우터의 SQL 11개), areas+report, bank_impact, 오류 로그(meta) | **옮기기 전에 응답 전체 고정 테스트 추가**(overview 는 지금 두 필드만 확인), Redis 를 켠 캐시 테스트 |
| 그대로 | calendar·visit 라우터, metrics, health, reports(CSP), admin, 작은 조회 라우터 | — |

6. **마무리**: 처음 보는 리뷰어 관점의 전체 검토(별도 에이전트), 정확성·요구사항에 영향 있는 것만 수정, 문서
