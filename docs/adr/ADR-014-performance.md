# ADR-014 측정 기반 성능 개선

- 상태: 채택 (2026-09-25)
- 측정: `make bench` (같은 도커 네트워크, 동시 16, 경로당 200회, uvicorn 워커 2, Apple Silicon) — [벤치마크 기록](../benchmarks.md)

## 병목과 조치
| 병목 (측정) | 원인 | 조치 | 결과 (p50 · 처리량) |
|---|---|---|---|
| 시군구 GeoJSON(772KB) 캐시 적중인데 p50 797ms | 요청마다 772KB 를 gzip 레벨 9 로 다시 압축 → 워커 2개 CPU 포화 | **gzip 으로 캐시**(mtime=0 결정적) + ETag 를 별도 키로 저장, `If-None-Match` 가 같으면 본문을 Redis 에서 꺼내지도 않고 304. 동적 JSON gzip 은 레벨 5 | 797→49ms · 19→223 req/s |
| 읍면동 GeoJSON 캐시 미적중 321ms | PostGIS 가 만든 `json` 을 드라이버가 dict 로 파싱 → 파이썬이 다시 직렬화 | SQL 에서 `CAST(… AS text)` 로 받아 그대로 이어 붙임 | 321→70ms (4.6×) |
| 지역 상세 74ms, 누적 1위 SQL | 조회마다 전체 지역·전 지표에 순위 창 함수 | 순위·백분위를 **계산 시점에 한 번**(V14 `rnk·pct·n`, `calc/10_ranks.sql`) | 74→28ms · 201→462 |

| 방문 여건 331ms | 250여 시군구 × 시간 예보 판정을 요청마다 파이썬에서 | 입력 버전(예보 발표·대기 발표·공휴일·계산·오늘)으로 캐시 키를 만들고, 적중 시 **직렬화된 문자열 그대로** 응답(dict 복원·재인코딩 생략) | 331→38ms · 47→392 |
| 기상청 수집 288초 | 격자 241곳을 순차 호출(호출당 약 1.2초가 대부분 응답 대기) | 스레드 4개로 동시 호출(서비스 한도 30tps 안), 적재는 한 스레드에서 차례로 | 288→74초 |

## 원칙
- 추측이 아니라 `make bench` + `pg_stat_statements`(V13, 느린 쿼리 500ms+ 로그)로 찾은 병목만 고친다.
- 캐시 무효화는 키에 데이터 버전(calc_run_id·발표 시각)을 넣는 방식 — 새 자료가 오면 키가 바뀌어 자연히 새로 계산.
- 관측: Prometheus `/metrics`(경로 템플릿 라벨 → 카디널리티 고정, 다중 워커 multiprocess 모드), 응답 `Server-Timing`·`X-Trace-Id`.
