# ADR-019 걸어서 가는 거리 — OSM 보행 그래프 · k-최근접 다중 출발 탐색 · 워커 자식 프로세스

- 상태: 채택 (2026-10-08)

## 맥락
- 지금까지 거리는 직선거리와 자동차 경로(카카오모빌리티)뿐이었다. 우체국을 가장 필요로 하는 고령층은 운전하지 않는 경우가 많다.
- 카카오는 공개 도보 경로 API 가 없고, 10만 집계구 × 수천 시설 점대점 호출은 한도·시간상 불가능하다.

## 결정
1. **도로망: OpenStreetMap 한국 추출본**(Geofabrik, 275MiB, ODbL) — 걸을 수 있는 길(인도·골목·일반 도로·국도, 고속도로·버스전용 제외,
   `foot=no`·통행 금지 제외)만. 내려받기는 `.md5` 로 무결성 확인, `Last-Modified` 가 같으면 다시 받지 않음.
2. **그래프는 워커에서 numpy/scipy 로**(pgRouting 대신) — 사용자 승인 사항.
   - DB 이미지를 직접 빌드할 필요가 없고, 수백만 간선의 경로 계산이 API 가 쓰는 DB 의 메모리·CPU 를 쓰지 않는다. 결과만 DB 에.
   - 두 번 읽기: (1) 길이 쓰는 노드 수를 세 교차점 확정 (2) 노드 좌표 캐시를 디스크(`sparse_file_array`)에 두고 교차점·끝점·150m 간격에서
     잘라 간선을 만듦. 177만 길 → 꼭짓점 447만 · 간선 537만, 4분(내려받기 포함). `.npz` 로 osm-data 볼륨에 저장(DB 에 넣지 않음).
   - 의존성(osmium·numpy·scipy)은 `atlas[walk]` 로 워커·수집기 이미지에만 설치, API 이미지는 그대로.
3. **k-최근접 다중 출발 다익스트라** — scipy 의 다중 출발(min_only)은 가장 가까운 한 곳만 준다. What-if·은행 지점 영향평가는
   '그곳이 닫히면 다음 곳'이 필요해, 꼭짓점마다 서로 다른 시설 라벨을 거리순 k개까지 확정하는 탐색을 직접 구현했다(우체국 3 · 은행 2).
   3km(고령자 약 1시간) 밖으로는 퍼지지 않아 빈 시골 도로망을 탐색하지 않는다. 무작위 그래프에서 시설마다 따로 최단 거리를 구한
   정답과 k=1·2·3 모두 일치하는지 테스트로 고정.
4. **걷는 속도 0.8m/s** — 서울시 보행약자 신호시간 기준(1m 당 1.25초, 일반 1m/s). 30분 = 1,440m. 설정으로 바꿀 수 있음.
5. **워커 자식 프로세스(`JobSpec.isolate`)** — 파이썬은 쓴 메모리를 OS 에 잘 돌려주지 않아, 그래프를 워커 프로세스에서 다루면 작업이
   끝난 뒤에도 1.16GB 가 남았다. osm·walk 작업은 spawn 자식 프로세스에서 돌려 끝나면 모두 반환(유휴 69MB), 자식이 죽어도 워커는 남는다.
6. **calc_run 마다** — 지표 계산이 끝나면 walk 작업이 자동으로 이어진다(`JobSpec.then`). 그래프가 없으면 건너뛴다(직선 지표는 그대로).

## 결과
- 전국 집계구 105,947곳 도보 거리 51초(우체국 k=3 24초 · 은행 k=2 16초). 3km 안에 금융 우체국이 닿는 집계구 87%.
- 지표 4개: 금융 우체국까지 걷는 거리(인구 가중) · 걸어서 30분 안에 금융 우체국이 없는 인구·비율 · 대면 금융 창구가 없는 인구.
  전국 **37.5%(1,939만 명)** 가 고령자 걸음으로 30분 안에 금융 우체국에 닿지 못한다(직선 2km 밖 13.9%).
- 도보/직선 비의 중앙값 1.41 — 일반적인 도로 우회 계수(1.2~1.4)와 맞아 그래프가 상식적인지 확인하는 지표로 씀.

## 한계
- OSM 은 인도·골목이 덜 그려진 지역이 있어 실제보다 멀게 나올 수 있다. 경사·계단·신호 대기는 반영하지 않는다.
- 간선 길이는 구면 하버사인(타원체 거리와 0.2% 안팎 차이). 3km 안에 닿지 않는 집계구는 지표에서 3km(하한)로 센다.
- 대표점 1개가 집계구를 대표한다(집계구 평균 500명이라 오차는 작지만 산간 집계구는 넓다).
